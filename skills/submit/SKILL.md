# submit — 제출 준비

## 순서
1. `time_status`. 15분 이하면 새 기능 금지.
2. 지시서의 **필수 산출물 목록**(파일명·경로·형식)을 다시 읽고 하나씩 있는지 본다. 과제가 지정한 문서 이름·양식이 있으면 그것이 우선이다.
3. 제출 문서를 만든다: 과제 지정 양식이 없으면 `.cofa/kit/templates/SUBMISSION.md` 를 복사해 채운다. 모든 `(작성)` 칸을 채우고, 모르는 것은 「미검증」 으로.
4. README 의 실행 방법을 **새 터미널에서 그대로 따라 해** 실제로 도는지 확인한다.
5. 테스트 전체를 마지막으로 한 번 돌리고 결과를 제출 문서에 붙인다.
6. `submission_check`(또는 `node .cofa/kit/scripts/kit.mjs check`) → 실패는 고치고, 경고는 고치거나 한계에 적는다.
7. 커밋: `git status --short` 로 변경 목록을 보여주고, 제출에 들어갈 파일만 `git add <파일…>` 한 뒤 `git commit -m "docs: 제출 문서와 최종 점검"`. 실험용·임시 파일은 넣지 않는다.
8. 담당자에게 보낼 **완료 보고 문안**을 만든다(사용자가 메신저로 보낼지 정한다). 5줄, 기술 용어 없이, 숫자 포함:
   ```
   요청하신 <무엇>을 만들었습니다.
   - 사용법: <한 줄>
   - 결과: <핵심 숫자>
   - 확인한 것: <검증 한 줄>
   - 아직 안 된 것: <한계 한 줄>
   ```
9. 사용자에게 알린다: 에디터 탭의 저장 상태가 「저장됨」인지 → 「제출하고 문제풀기」(미리보기, 일부 파일만 보일 수 있음) → 「제출물 확정하고 문제풀기」(확정 뒤 수정 불가) 두 단계.
10. 시간이 남으면 `$explainback`.

## 제출 문서 작성 규칙 (읽는 사람이 사람이든 AI 든 같다)
- 모든 주장에 근거를 붙인다: 파일:함수, 증거 번호(`.cofa/evidence`), 수치, 담당자 답 인용.
- 어느 과제에나 붙일 수 있는 문장은 쓰지 않는다: 「효율적이고 확장 가능한」 「사용자 친화적인」 「성공적으로 구현」 「다양한」 「최적화된」. 지우고 구체적인 사실로 바꾼다.
- 과장하지 않는다: 미검증은 미검증, 안 된 것은 「한계」 에 먼저 적는다.
- 짧게: 문장 하나에 사실 하나. 표와 숫자가 문단보다 낫다. 서론·맺음말·요약 반복을 넣지 않는다.
- 결정은 사용자가 한 말로: 설계안을 고른 이유는 사용자가 말한 한 줄을 그대로 쓴다(DECISIONS.md). 사용자가 서술형에서 같은 말로 설명할 수 있어야 한다.
- 다 쓴 뒤 스스로 점검: 위 금지 표현 검색, 근거 없는 문장 표시, 사용자가 설명 못 할 문장 표시.

## 제출 문서에 반드시 있을 것
- 무엇을 만들었나(한 단락)와 실행 방법(명령 그대로)
- 요구사항별 충족 여부와 증거(REQUIREMENTS.md 요약)
- 주요 결정과 이유(DECISIONS.md 요약)
- 한계·미검증·다음 개선
- AI 활용 방식(무엇을 맡기고 무엇을 직접 검증했나)
