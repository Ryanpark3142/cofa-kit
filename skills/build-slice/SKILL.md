# build-slice — 한 슬라이스 구현 (메인 세션)

## 순서
1. PLAN.md 에서 이번 슬라이스의 요구 ID·바꿀 파일·검증 방법을 읽는다. 그 파일이 다른 탭의 작업(T)에 배정돼 있으면 건드리지 않고 사용자에게 알린다(`kit.mjs board`).
2. 관련 파일만 읽고 할 일을 3줄로 말한다(무엇 · 어느 파일 · 어떻게 확인).
3. 검증 방법을 테스트나 실행 스크립트로 먼저 쓴다(가능하면).
4. 최소한으로 구현한다. 요구 ID 와 무관한 정리·리팩터링은 하지 않는다.
5. 실행하기 **전에 예상 결과를 한 줄** 말한다(예: 「테스트 5개 통과, 빈 입력은 400」). 그다음 `node .cofa/kit/scripts/kit.mjs run --req <요구 ID> -- <명령>`. 결과를 그대로 보여 주고, 예상과 다르면 그 차이부터 짚는다. 통과하면 요구 상태·증거가 자동으로 갱신된다.
   웹이면 서버를 `0.0.0.0` 으로 백그라운드에 띄우고 포트·경로를 알려준다(사용자가 Browser 탭에서 확인). 확인용 `curl` 을 `kit.mjs run` 으로 남긴다.
6. 통과하면: 설계 선택이 있었을 때만 `kit.mjs decision`, 그다음 `node .cofa/kit/scripts/kit.mjs commit -m "<type>: <무엇> (<요구 ID>)" <바꾼 파일…>`.
7. 실패하면 `$debug`. 같은 수정을 두 번 넘게 반복하지 않는다.

## 보고 (짧게, 「흐름」 줄은 사용자가 나중에 설명할 재료)
「흐름」 은 일반론(「읽기 → 계산 → 출력」)이 아니라 **실제 입력값 하나가 어느 파일:함수를 거쳐 어떤 출력값이 되는지**를 쓴다.
```
슬라이스 N 완료 (R2, R3) — 커밋 a1b2c3d
- 변경: src/x.py 의 parse(), tests/test_x.py
- 검증: 증거 #5 `python3 -m pytest -q` → 5 passed (예상 5 passed)
- 흐름: `POST /todos {"title":"우유"}` → app.py:create_todo() → todos 에 id 1 추가 → 201
- 미검증: 빈 파일 입력
- 다음: 슬라이스 N+1 (파일이 안 겹치는 슬라이스가 있으면 `$delegate` 로 다른 탭에)
- 설명: 공부 탭에서 `ㄱ`
```
처음 나온 용어가 있으면 보고 끝에 한 줄로 정의한다. 더 깊은 설명은 사용자가 다른 탭에서 `$explain` 으로 한다.

## 금지
- 여러 슬라이스를 한 번에
- 테스트를 통과시키려고 테스트를 고치기(요구가 바뀐 경우만, 이유를 말하고)
- 실행하지 않고 "동작할 것입니다"
