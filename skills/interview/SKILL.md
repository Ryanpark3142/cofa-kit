# interview — 담당자 질문 루프

담당자는 업무 상황과 판단 기준을 아는 사람이다. 코드 설계를 대신 정해 주지 않는다. 요구는 한 번에 다 나오지 않게 설계돼 있으니, **작고 구체적인 질문을 여러 번** 하는 것이 핵심이다. 「해야 할 일을 1, 2, 3으로 알려 주세요」 같은 통째 질문은 막혀 있거나 점수가 낮다.

## 좋은 질문의 조건
- 한 번에 하나만 묻는다.
- 내가 본 근거를 붙인다: "데이터에 `status` 값이 A/B/C 세 가지인데…"
- 선택지를 준다: "① 제외 ② 0으로 처리 ③ 따로 표시 중 어느 쪽인가요?"
- 답에 따라 무엇이 달라지는지 내가 안다(아니면 묻지 않는다).

## 질문 순서
1. **최근 사례**: "최근에 이 일 때문에 곤란했던 때를 하나만 말씀해 주시겠어요?"
2. **지금 처리 방식**: 지금은 누가 어떻게 하고, 어디서 시간이 드나
3. **성공 숫자**: 지금 값과 목표 값, 어디서 재나
4. **예외**: 규칙이 안 맞는 경우, 겹치는 경우
그다음 아래 분야에서 결과를 바꾸는 것만 묻는다.

## 기본안을 붙여 묻기
답이 늦을 수 있으니 "A 로 하려는데 괜찮을까요? 아니면 B 인가요?" 처럼 기본안을 붙여 묻고, 답을 기다리는 동안 기본안 가정으로 다른 작업을 진행한다(가정임을 `req_upsert` source `추론` 으로 남긴다).

## 구현 전 합의문
요구가 어느 정도 모이면 담당자에게 한 번 보내 확인받는다.
```
정리한 내용이 맞는지 확인 부탁드립니다.
- 문제: …  - 병목: …  - 성공 기준: …(숫자)
- 이번에 만들 것: …  - 이번에 안 만들 것: …  - 제약: …
```

## 질문 분야 (결과를 바꾸는 것부터)
1. **사용자·목적**: 결과를 누가, 언제, 어떤 결정에 쓰는가? 지금은 어떻게 하고 있는가(현재 방식의 불편)?
2. **성공 기준**: "잘 됐다"를 무엇으로 판단하나? 숫자 기준(정확도·처리 시간·건수)이 있나?
3. **입력**: 데이터 출처·갱신 주기·규모, 이상값·결측의 의미, 단위·시간대
4. **규칙·예외**: 경계값 포함 여부(이상/초과), 우선순위가 겹칠 때, 예외 케이스를 실제로 겪은 사례
5. **출력**: 형식(화면·파일·API), 필수 항목, 정렬·단위·표기
6. **범위·우선순위**: 시간이 모자라면 무엇을 먼저? 이번에 안 해도 되는 것은?
7. **제약**: 써야 하는/쓰면 안 되는 기술, 보안·개인정보

## 답을 받은 뒤
1. 사용자가 붙여 넣은 답을 원문 그대로 근거로 쓴다. 답을 지어내지 않는다.
2. 요구 추가·수정: `req_upsert`(source `담당자`). 기존 추론 요구가 확인되면 source 를 `담당자`로 바꾼다.
3. 답이 모호하면 후속 질문 하나를 만든다(예: "‘대부분’이면 몇 % 이상인가요?").
4. 설계가 바뀌면 `log_decision`, 진행 기록은 `log_work`("담당자: ~ 확인 → R3 수정").
5. 구현 중에도 판단이 갈리는 지점이 나오면 이 스킬로 돌아온다.

## 출력 형식
```
[질문 1] (분야: 규칙·예외 / 바뀌는 것: R2 필터 조건)
<담당자에게 그대로 보낼 문장>
```
