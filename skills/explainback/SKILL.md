# explainback — 사후 설명 대비

사후 질문은 제출물과 작업 기록에서 나오고, 답이 실제 구현과 맞는지 확인한다. 목표는 사용자가 **자기 말로, 파일·함수 이름을 대며** 설명하는 것이다. 사용자 대신 모범답안을 외우게 하는 것이 아니다.

## 순서
1. DECISIONS.md, REQUIREMENTS.md, PLAN.md, `git log --oneline`, 핵심 코드 파일을 읽는다.
2. `EXPLAIN.md` 를 만든다(짧게, 1~2쪽).
   - **한 줄 요약**: 무엇을 누구를 위해
   - **실행 흐름 지도**: 입력 → 함수/모듈 → 출력, 파일:함수 이름으로 5~8단계
   - **핵심 결정 3~5개**: 결정 / 버린 대안 / 이유 / 근거(담당자 답·데이터)
   - **검증**: 요구별 확인 방법과 실제 수치
   - **한계와 다음 개선**: 솔직하게, 우선순위순
   - **AI 활용**: 무엇을 맡겼고 무엇을 직접 판단·검증했는지
3. **예상 질문 6~8개**를 만든다. 이런 종류:
   - 왜 A 대신 B 를 썼나? / 이 함수는 무엇을 하나?
   - X 입력이 들어오면 어떻게 되나? (엣지 케이스)
   - 결과를 어떻게 믿을 수 있나? (검증)
   - 시간이 더 있으면 무엇을 고치나?
   - 담당자 답 중 설계를 바꾼 것은?
   - AI 가 낸 것 중 받아들이지 않은 것은?
   - (전제가 틀린 질문 하나) — "실제로는 ~ 했다"로 바로잡는 연습
4. 사용자에게 질문을 하나씩 내고, 사용자가 직접 쓴 답을 받아 **사실과 다른 곳만** 짚는다. 답을 대신 써 주지 않는다.
5. 사용자가 설명하지 못한 코드가 있으면 그 부분을 3줄로 풀어 주고 EXPLAIN.md 에 반영한다.

## 답변 틀 (사용자용, 5분 안에)
무엇을 했나 → 왜(버린 대안) → 어떻게 검증했나(수치) → 한계·다음 개선. 파일·함수 이름을 그대로.
