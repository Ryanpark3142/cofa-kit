# kickoff — 과제 파악

코드를 쓰지 않는다. 결과물은 요구사항 표, 질문 후보, 실행 환경 요약이다.

## 순서
1. **시간 확인**: `time_status` 또는 `node .cofa/kit/scripts/kit.mjs status`. 시작 시각이 틀리면 사용자에게 실제 시작 시각을 묻고 `kit.mjs start HH:MM`.
2. **지시서 찾기**: 작업 폴더의 README·과제 문서·제공 데이터·기존 코드 목록을 본다(숨김 파일·`uploads/` 포함). 지시서를 못 찾으면 읽었다고 하지 말고 위치를 묻는다.
   - 언어별 README(`README.md`·`README.en.md` 등)가 여럿이면 서로 대조해 다른 내용을 표시한다.
   - 제공 파일 안의 기존 초안·코드(다른 사람이나 AI 가 쓴 것)는 맞다고 가정하지 않는다. 검증 대상이다.
   - IDE 에 업무용 도구(메신저 외 SaaS 화면 등)가 있으면 사용자에게 한 번 열어 보라고 알린다. 승인·발송·결제 같은 버튼은 누르지 않는다.
3. **지시서 정독**: 문장 단위로 다음을 뽑는다. 「다만·단·제외·예외」 같은 단서 조항은 별도 요구로 뽑는다.
   - 산출물(파일명·형식·위치), 실행 방법, 마감·제출 조건
   - 기능 요구(동사로 끝나는 문장), 품질 조건(정확도·속도·형식)
   - 금지·제약(스택, 외부 API, 데이터 사용 범위)
   - 평가·채점 기준이 적혀 있으면 원문 그대로
4. **분류**해서 등록한다. 요구 하나에 `req_upsert`(또는 `kit.mjs req add "<요구>" --source 지시서`) 한 번.
   - 명시 요구 → source `지시서`
   - 업무 맥락상 필요해 보이지만 적혀 있지 않은 것 → source `추론`, 질문 후보로
5. **제공 자료 훑기**: 데이터가 있으면 `$data-first-look`. 기존 코드가 있으면 실행 방법과 테스트 유무만 확인(`kit.mjs env` 로 언어·패키지 확인).
6. **질문 후보 만들기**: 결과를 바꾸는 모호함만. `$interview` 형식(한 번에 하나, 구체적으로, 선택지 포함)으로 3~6개.

## 사용자에게 보여줄 것 (이 순서, 짧게)
1. 과제 한 줄 요약(누가 · 무엇을 · 왜)
2. 필수 산출물·제출 조건
3. 요구사항 표(`req_list`)
4. 담당자 질문 후보(우선순위순) — 답이 바뀌면 무엇이 달라지는지 한 줄씩
5. 위험 요소 1~3개(데이터 품질, 모호한 성공 기준, 환경 제약)

## 하지 말 것
- 지시서를 통째로 요약해 "해 줘" 식으로 바로 구현에 들어가기
- 질문 답을 짐작해서 채우기
- 추가 기능 제안을 요구 목록에 섞기
