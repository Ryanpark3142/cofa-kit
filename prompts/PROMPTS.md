# 프롬프트 모음

Codex 에 그대로 붙이거나 조금 고쳐 쓰는 요청문. 공통 틀은 **목표 / 범위(파일) / 제약 / 완료 기준 / 보고 형식**이다.
`<>` 는 바꿔 쓸 자리.

---

## 0. 설치 (시험장 첫 1분)

```
https://github.com/<아이디>/<저장소> 를 /tmp/kit 에 clone 하고 `bash /tmp/kit/install.sh` 를 작업 폴더에서 실행해줘.
출력에 나온 실행 환경 요약을 3줄로 알려줘.
```

설치 후 Codex 를 다시 열면 AGENTS.md 와 스킬이 읽힌다. 확인: `지금 적용된 AGENTS.md 규칙을 3줄로 요약하고 쓸 수 있는 스킬 이름을 나열해줘.`

## 1. 파악 (0~15분)

**시작**
```
$kickoff 과제 지시서를 읽고 요구사항을 정리해줘. 코드는 아직 쓰지 마.
```

**지시서가 길 때**
```
지시서에서 ①산출물(파일명·형식) ②기능 요구 ③품질 조건 ④금지·제약 ⑤평가 기준 문장을 원문 위치와 함께 뽑아줘.
요약하지 말고 원문 문장을 그대로.
```

**모호한 점만**
```
요구사항 표에서 해석이 두 가지 이상 가능한 항목만 골라, 해석별로 구현이 어떻게 달라지는지 한 줄씩 적어줘.
```

## 2. 담당자 질문

**질문 만들기**
```
$interview 지금까지 알게 된 것 기준으로 담당자에게 물을 질문 3개를 우선순위대로 만들어줘.
각 질문은 한 번에 하나만 묻고, 내가 본 근거와 선택지를 붙이고, 답에 따라 바뀌는 요구 ID 를 적어줘.
```

**답 반영**
```
담당자 답변: "<붙여 넣기>"
이 답으로 바뀌는 요구를 req_upsert 로 갱신하고, 설계가 바뀌면 log_decision 으로 남겨줘. 모호한 부분이 있으면 후속 질문 하나만.
```

**직접 보낼 질문 예시** (담당자에게 그대로, 하나씩)
- 이 결과를 실제로 누가, 어떤 결정을 할 때 보나요? 지금은 그 일을 어떻게 하고 계세요?
- "잘 됐다"는 걸 무엇으로 판단하시나요? 숫자 기준이 있나요(예: 정확도 몇 %, 처리 몇 초)?
- 데이터의 `<열>` 이 비어 있는 행이 `<n>`개인데, ① 제외 ② 0 처리 ③ 따로 표시 중 어느 쪽이 맞나요?
- 기준값 `<값>` 은 "이상"인가요 "초과"인가요?
- 두 규칙이 동시에 해당하면 어느 쪽이 우선인가요? 실제로 그런 사례가 있었나요?
- 결과는 화면, 파일, 보고서 중 어떤 형태가 가장 쓰기 편하세요? 꼭 들어가야 하는 항목은요?
- 시간이 부족하면 무엇부터 되어 있어야 하나요? 이번에 안 해도 되는 건 무엇인가요?
- 예외로 다뤄야 하는 대상(특정 설비·고객·기간)이 있나요?
- `<코드값>` 은 무슨 뜻인가요? 단위는 무엇인가요?
- 이전에 비슷한 걸 시도했다가 안 된 적이 있나요? 왜 안 됐나요?

## 3. 계획 (15~30분)

```
$plan 요구사항 표 기준으로 설계안 2개를 비교표로 내고 추천 하나와 이유를 말해줘. 이미 설치된 도구를 우선해.
각 구성요소가 어느 요구 ID 때문에 필요한지 붙이고, 이유가 없는 것은 빼줘. 코드는 아직 쓰지 마.
```

```
<선택안>으로 간다. log_decision 으로 남기고 PLAN.md 를 슬라이스 표로 채워줘.
첫 슬라이스는 입력에서 출력까지 가장 얇게 도는 판으로. 슬라이스마다 검증(입력 → 기대 출력, 명령)을 먼저 적어줘.
```

## 4. 구현

```
$build-slice 슬라이스 <N> 만 구현해. 수정 파일은 <a>, <b> 로 한정.
검증 방법을 테스트로 먼저 만들고, 구현 후 실행 결과를 그대로 보여줘. 통과하면 req_upsert·log_work·커밋.
```

```
지금 변경을 커밋 단위로 나눠서 커밋해줘. 메시지는 "<type>: <무엇> (<요구 ID>)".
```

## 5. 디버깅

```

<오류 원문 붙여 넣기>
```

```
같은 방법으로 두 번 실패했어. 지금까지 시도한 것과 결과를 표로 정리하고, 다른 접근 2개와 각각의 시간을 제안해줘.
```

## 6. 위임 (긴 구현 병렬)

```
$delegate <모듈/작업>을 위임 지시서로 만들어 .cofa/tasks/T1.md 에 저장해줘. 수정 가능한 파일, 입출력 계약, 완료 기준 명령, 하지 말 것을 포함해서.
```
새 터미널에서: `codex exec "$(cat .cofa/tasks/T1.md)"`
돌아오면:
```
T1 결과를 검증해줘. git diff --stat 으로 허용 파일만 바뀌었는지 보고 완료 기준 명령을 직접 다시 실행해.
```

## 7. 검증 (130분 전후)

```
$verify 요구사항별로 확인 방법을 정하고 실제로 실행해서 표로 보여줘. 증거 없는 건 미검증으로.
테스트가 0건을 대상으로 돌지 않았는지 처리 건수도 출력해줘.
```

```
엣지 케이스 5개(빈 입력, 경계값, 잘못된 형식, 중복, 큰 입력)를 실행해 보고 결과를 표로. 고치지 말고 먼저 보고만.
```

```
핵심 숫자 <지표>를 지금 코드와 다른 방법(작은 표본 손계산이나 다른 경로)으로 다시 계산해서 일치하는지 확인해줘.
```

## 10. 사후 설명 대비 (제출 직전)

```
$explainback EXPLAIN.md 를 만들고 예상 질문 6개를 하나씩 내줘. 내가 직접 답을 쓸 테니 사실과 다른 부분만 짚어줘. 답을 대신 써 주지 마.
```

```
<파일:함수> 가 무엇을 하는지 내가 설명하지 못하겠어. 입력·처리·출력을 3줄로 풀어 주고, 왜 이렇게 짰는지 DECISIONS.md 근거로 알려줘.
```

**서술형 답변 틀 (AI 금지 단계, 직접 타이핑, 문항당 5분)**
1. 무엇을 했나 — 파일·함수 이름으로
2. 왜 — 버린 대안과 이유, 담당자 답·데이터 근거
3. 어떻게 검증했나 — 명령과 수치
4. 한계와 다음 개선
질문 전제가 실제 구현과 다르면 "실제로는 ~ 했다"로 먼저 바로잡는다.
