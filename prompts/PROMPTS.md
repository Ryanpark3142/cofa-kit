## 0. 설치 (시험장 첫 1분)

**터미널에 직접 친다**(승인 창 없이 바로 끝난다). 작업 폴더에서:
```bash
git clone --depth 1 https://github.com/Ryanpark3142/cofa-kit /tmp/kit && bash /tmp/kit/install.sh
```
git clone 이 막히면(HTTPS 다운로드만 될 때):
```bash
mkdir -p /tmp/kit && curl -fsSL https://codeload.github.com/Ryanpark3142/cofa-kit/tar.gz/refs/heads/main | tar xz -C /tmp/kit --strip-components=1 && bash /tmp/kit/install.sh
```
Codex 에 시킬 때(체험에서 성공, 승인 2번):
```
github.com/Ryanpark3142/cofa-kit 를 /tmp/kit 에 받아서 README 대로 설치해줘
```

설치 후 Codex 를 **승인 창 없이** 연다(이미 열려 있으면 끄고 다시). 탭을 새로 열 때마다 같은 명령:
```bash
codex --yolo
```
`--yolo` 는 `--dangerously-bypass-approvals-and-sandbox` 의 짧은 이름이다. 거부되면 `codex` 로 열고 `/permissions` → `Full Access`. 폴더 신뢰를 물으면 신뢰한다. 확인(한 번만): `파일을 열지 말고, 지금 받은 지침에 있는 cofa-kit 원칙 6개의 제목과 쓸 수 있는 스킬 이름만 말해줘.`

## 2. 담당자 질문

**질문 만들기**
```
$interview 지금까지 알게 된 것 기준으로 담당자에게 물을 질문 3개를 우선순위대로 만들어줘.
각 질문은 한 번에 하나만 묻고, 내가 본 근거와 선택지를 붙이고, 답에 따라 바뀌는 요구 ID 를 적어줘.
```

**답 반영**
```
담당자 답변: "<붙여 넣기>"
이 답으로 바뀌는 요구를 갱신하고(출처 담당자), 설계가 바뀌면 결정으로 남겨줘. 모호한 부분이 있으면 후속 질문 하나만.
```

**직접 보낼 질문 예시** (담당자에게 그대로, 하나씩)
- 이 결과를 실제로 누가, 어떤 결정을 할 때 보나요? 지금은 그 일을 어떻게 하고 계세요?
- "잘 됐다"는 걸 무엇으로 판단하시나요? 숫자 기준이 있나요(예: 정확도 몇 %, 처리 몇 초)?
- 데이터의 `<열>` 이 비어 있는 행이 `<n>`개인데, ① 제외 ② 0 처리 ③ 따로 표시 중 어느 쪽이 맞나요?
- 기준값 `<값>` 은 "이상"인가요 "초과"인가요?
- 두 규칙이 동시에 해당하면 어느 쪽이 우선인가요? 실제로 그런 사례가 있었나요?
- 결과는 화면, 파일, 보고서 중 어떤 형태가 가장 쓰기 편하세요? 꼭 들어가야 하는 항목은요?
- 시간이 부족하면 무엇부터 되어 있어야 하나요? 이번에 안 해도 되는 건 무엇인가요?
- 예외로 다뤄야 하는 대상(특정 설비·고객·기간)이 있나요?
- `<코드값>` 은 무슨 뜻인가요? 단위는 무엇인가요?
- 이전에 비슷한 걸 시도했다가 안 된 적이 있나요? 왜 안 됐나요?

## 10. 사후 설명 대비 (제출 직전)

```
$explainback EXPLAIN.md 를 만들고 예상 질문 6개를 하나씩 내줘. 내가 직접 답을 쓸 테니 사실과 다른 부분만 짚어줘. 답을 대신 써 주지 마.
```

```
$explain <파일:함수> 가 무엇을 하는지 모르겠어. 원리 한 문장 먼저, 그다음 실제 입력값 하나로 처음부터 끝까지 따라가 줘. 왜 이렇게 짰는지는 DECISIONS.md 근거로.
```

작업 중 이해가 안 갈 때(언제든):
```
$explain 이해 안 가: <방금 나온 것>. 한 토막만, 처음 나온 용어는 정의부터.
```

**서술형 답변 틀 (AI 금지 단계, 직접 타이핑, 문항당 5분)**
1. 무엇을 했나 — 파일·함수 이름으로
2. 왜 — 버린 대안과 이유, 담당자 답·데이터 근거
3. 어떻게 검증했나 — 명령과 수치
4. 한계와 다음 개선
질문 전제가 실제 구현과 다르면 "실제로는 ~ 했다"로 먼저 바로잡는다.
